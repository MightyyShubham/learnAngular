Router setup with provideRouter and feature functions

Starting from Angular 15, Angular introduced the standalone API, where we can configure routing without using AppRoutingModule.

Instead of importing RouterModule.forRoot(), we use provideRouter() inside app.config.ts or during application bootstrap.

provideRouter() accepts two things:

  • Route definitions
  • Optional feature functions

Feature functions allow us to enable router features like preloading, debugging, scrolling, hash-based navigation, and component input binding in a modular and tree-shakable way.

This approach reduces boilerplate, improves tree shaking, and aligns with Angular's standalone architecture. Angular introduced provideRouter() as part of its standalone architecture. It removes the dependency on NgModule, reduces boilerplate, improves tree shaking through feature functions, and offers a more modular way to configure routing. RouterModule.forRoot() is still supported for applications that continue to use NgModules.

Feature functions enable optional router capabilities:

  • withPreloading(): Used to preload lazy-loaded modules after the initial application load.
  • withDebugTracing(): Prints all router events.
  • withComponentInputBinding(): Automatically binds route parameters to component inputs.
  • withInMemoryScrolling(): Restores scroll position.
  • withHashLocation(): Useful when the server cannot support HTML5 push-state routing.
  • withNavigationErrorHandler(): Lets you define a global handler for navigation errors.
providers: [
  provideRouter(
      routes,
      withDebugTracing(),
      withPreloading(PreloadAllModules),
      withComponentInputBinding(),
      withInMemoryScrolling({ 
          scrollPositionRestoration: 'enabled'
      } )
  )
]

Functional redirects — redirectTo as a function receiving params and query params

In Angular 17+, redirectTo can be a function instead of a static string. This function receives the current route information, including route parameters and query parameters, allowing dynamic redirects based on runtime conditions.

path: 'search',
redirectTo: ({  queryParams } ) =>
  `/products?category=${ queryParams['category']} `

Lazy loading with loadComponent and loadChildren

Lazy loading is a technique where Angular loads code only when it's needed, reducing the initial bundle size and improving application startup time.

loadComponent is used to lazy load a standalone component.

loadChildren is used to lazy load a feature module or a standalone route configuration.

{ 
  path: 'profile',
  loadComponent: () =>
    import('./profile/profile.component')
      .then(m => m.ProfileComponent)
} 
{ 
  path: 'admin',
  loadChildren: () =>
    import('./admin/admin.routes')
      .then(m => m.ADMIN_ROUTES)
} 

import {  Routes }  from '@angular/router';

export const ADMIN_ROUTES: Routes = [
  { 
    path: '',
    loadComponent: () =>
      import('./admin.component').then(m => m.AdminComponent)
  } 
];

Navigation with routerLink, routerLinkActive, and ariaCurrentWhenActive

Angular provides the routerLink directive for client-side navigation without reloading the page. routerLinkActive adds CSS classes when a route is active, and ariaCurrentWhenActive improves accessibility by setting the aria-current attribute for screen readers.

<a
  routerLink="/home"
  routerLinkActive="active">
  Home
</a>

Route parameters and withComponentInputBinding — params, query params, and resolved data as component inputs

withComponentInputBinding() automatically binds route params, query params, and resolved data to a component's @Input() properties. This removes the need to inject ActivatedRoute and manually read values.

// Traditional approach:
constructor(private route: ActivatedRoute) { } 

ngOnInit() { 
  const id = this.route.snapshot.params['id'];
} 
// Route configuration:
{ 
  path: 'user/:id',
  component: UserComponent
} 
// Component input binding:
import {  Input }  from '@angular/core';

export class UserComponent { 
  @Input() id!: string;
}

Resolvers — ResolveFn, skipping HTTP with navigation state

A Resolver fetches data before a route is activated. Using ResolveFn, Angular waits for the data to load and then passes it to the component, preventing empty screens or loading spinners. If the data is already available, we can pass it using navigation state and skip the HTTP request.

import {  ResolveFn }  from '@angular/router';

export const userResolver: ResolveFn<User> = (route) => { 
  return inject(UserService).getUser(route.params['id']);
} ;
{ 
  path: 'user/:id',
  component: UserComponent,
  resolve: { 
    user: userResolver
  } 
}

Skipping HTTP with Navigation State

Suppose you're on the Users List page and already have the user object. Instead of calling the API again:

this.router.navigate(['/user', user.id], { 
  state: {  user } 
} );
const user = history.state.user;

Pass the data using router.navigate(..., { state } ) and read it from history.state in the target component.

ResolveFn loads data before navigation, and navigation state can be used to pass existing data and avoid unnecessary HTTP requests.

Child routes, nested outlets, and relativeTo navigation

Child routes allow us to create nested URLs and layouts. They are rendered inside a nested <router-outlet>. relativeTo is used for relative navigation instead of navigating from the application's root.

const routes: Routes = [
  { 
    path: 'dashboard',
    component: DashboardComponent,
    children: [
      {  path: 'profile', component: ProfileComponent } ,
      {  path: 'settings', component: SettingsComponent } 
    ]
  } 
];

Without relativeTo:

this.router.navigate(['/dashboard/settings']);

With relativeTo:

this.router.navigate(['settings'], { 
  relativeTo: this.route
} );

Why Use relativeTo?

  • Avoid hardcoded full paths.
  • Easier to maintain when route structures change.
  • Useful for navigation within child routes.

Route-scoped providers — services created and destroyed with a route subtree

Route-scoped providers allow us to create services that are available only within a specific route and its child routes. The service instance is created when the route loads and destroyed when that route subtree is removed. This helps isolate state and avoid keeping unnecessary services alive globally.

{ 
  path: 'admin',
  component: AdminComponent,
  providers: [
    AdminService
  ],
  children: [
    { 
      path: 'users',
      component: UsersComponent
    } 
  ]
}

Q. Where can we define route-scoped providers?

A: Inside the providers array of a route configuration.

Q. When is the service destroyed?

A: When the route subtree that created it is destroyed.

Q. Why not always use providedIn: 'root'?

A: Root services live for the entire application lifecycle and may share state unnecessarily.

Query parameters and queryParamsHandling (preserve, merge)

Query parameters are optional URL parameters used to pass additional information like filters, sorting, or pagination. Angular provides queryParamsHandling to control how existing query parameters behave during navigation. It supports merge to combine old and new parameters, and preserve to keep existing parameters unchanged.

/products?page=2&category=mobile
page = 2
category = mobile
<a 
  routerLink="/products"
  [queryParams]="{ category:'mobile'} ">
  Products
</a>
this.router.navigate(['/products'], { 
  queryParams: { 
    category: 'mobile'
  } ,
  queryParamsHandling: 'merge'
} );

canActivate — authentication guard with redirect to login and return URL

canActivate is a route guard that decides whether a user can access a route before navigation happens. A common use case is authentication. If the user is logged in, navigation continues. Otherwise, the user is redirected to the login page, and the original URL is stored as a return URL so the user can be redirected back after successful login.

export const authGuard: CanActivateFn = (route, state) => { 
  const authService = inject(AuthService);
  const router = inject(Router);

  if (authService.isLoggedIn()) { 
    return true;
  } 

  return router.createUrlTree(['/login'], { 
    queryParams: { 
      returnUrl: state.url
    } 
  } );
} ;

Route Configuration

{ 
  path: 'dashboard',
  component: DashboardComponent,
  canActivate: [authGuard]
}

canActivate protects routes by checking authentication before navigation; unauthenticated users are redirected to login with a returnUrl to continue their original navigation after login.

canActivateChild — protecting an entire child route subtree

canActivateChild is a route guard used to protect all child routes of a parent route. Instead of adding canActivate to every child route individually, we apply canActivateChild on the parent route, and Angular checks the guard before activating any child route.

{ 
  path: 'admin',
  component: AdminComponent,
  canActivateChild: [authGuard],
  children: [
    { 
      path: 'users',
      component: UsersComponent
    } ,
    { 
      path: 'settings',
      component: SettingsComponent
    } 
  ]
}

Q. When should you use canActivateChild?

A: When multiple child routes require the same authorization check.

Q. Does canActivateChild protect the parent route also?

A: No. It only protects child route activation. Use canActivate for the parent route itself.

canActivateChild protects an entire child route tree using a single guard instead of adding guards to every child route individually.

canMatch — feature-flag guard and auth guard; difference from canActivate

canMatch is a route guard that decides whether Angular should match a route during route selection. If it returns false, Angular skips that route and tries another matching route. It is commonly used for feature flags and conditional lazy loading.

canActivate runs after a route is matched and decides whether the user can enter that route.

export const routes: Routes = [
  { 
    path: 'new-dashboard',
    canMatch: [featureFlagGuard],
    loadComponent: () =>
      import('./new-dashboard.component')
        .then(m => m.NewDashboardComponent)
  } ,
  { 
    path: 'new-dashboard',
    component: OldDashboardComponent
  } 
];
export const featureFlagGuard: CanMatchFn = () => { 
  const featureService = inject(FeatureService);

  return featureService.isNewDashboardEnabled();
} ;

Q. Can canMatch replace canActivate?

A: No. canMatch controls route selection, while canActivate controls access after matching.

Q. Why is canMatch better for lazy loading?

A: Because if canMatch returns false, Angular does not load the lazy route bundle.

Navigation extras: state, info, replaceUrl, skipLocationChange, browserUrl

Navigation extras are additional options passed during Angular navigation using router.navigate() or routerLink. They control how navigation behaves, what data is passed, and how the browser URL/history is updated.

Common extras are:

  • state → pass data to the next route
  • info → attach temporary navigation information
  • replaceUrl → replace current browser history entry
  • skipLocationChange → navigate without changing browser URL
  • browserUrl → show a different URL in the address bar

1. state — Pass Data During Navigation

this.router.navigate(['/user', 101], { 
  state: { 
    userName: 'John'
  } 
} );

// Read in target component:
const data = history.state.userName;
// Output: John

Use Case: Passing already loaded data and avoiding another API call.

2. info — Temporary Navigation Information

this.router.navigate(['/photo'], { 
  info: { 
    source: 'gallery'
  } 
} );

Difference:

  • state: Stored in browser history; available after navigation; good for data passing.
  • info: Not stored in browser history; available only during current navigation; good for navigation behavior (e.g., animation direction, navigation source tracking).

3. replaceUrl

Normally: Login → Dashboard (Press Back → Login)

this.router.navigate(['/dashboard'], { 
  replaceUrl: true
} );

History becomes Dashboard. Back button will not return to login. Common use case: After login redirection.

4. skipLocationChange

Navigation happens but browser URL does not change.

this.router.navigate(['/admin'], { 
  skipLocationChange: true
} );
// Before: /app
// After navigation: Browser URL shows /app, actual route is /admin

Use Case: Internal navigation, wizard steps, hidden routes.

5. browserUrl

Allows displaying a different URL in the browser address bar.

this.router.navigate(['/product/123'], { 
  browserUrl: '/iphone'
} );
// Angular route: /product/123
// Browser shows: /iphone

Useful for: SEO-friendly URLs, custom displayed URLs.

RedirectCommand — redirecting with state from a guard

RedirectCommand is used inside Angular guards when we need to redirect the user and also pass navigation extras like state. Unlike returning a simple UrlTree, RedirectCommand allows us to attach additional navigation options during the redirect.

Why RedirectCommand?

Before: return router.createUrlTree(['/login']); (Cannot pass navigation extras like state).

With RedirectCommand:

return new RedirectCommand(
  router.parseUrl('/login'),
  { 
    state: { 
      message: 'Please login first'
    } 
  } 
);

Example: Auth Guard

export const authGuard: CanActivateFn = () => { 
  const auth = inject(AuthService);
  const router = inject(Router);

  if (auth.isLoggedIn()) { 
    return true;
  } 

  return new RedirectCommand(
    router.parseUrl('/login'),
    { 
      state: { 
        returnUrl: '/dashboard'
      } 
    } 
  );
} ;

Reading State in Login Component:

const returnUrl = history.state.returnUrl;
console.log(returnUrl); // Output: /dashboard

// After login:
this.router.navigateByUrl(returnUrl);

Router configuration: paramsInheritanceStrategy, onSameUrlNavigation, urlUpdateStrategy

Angular Router provides configuration options to control how route parameters are inherited, how navigation to the same URL behaves, and when the browser URL is updated during navigation.

1. paramsInheritanceStrategy

Controls how child routes inherit parameters and data from parent routes.

Default: paramsInheritanceStrategy: 'emptyOnly' (Child gets parent params only when child route has no own component or parent is an empty-path route).

// Use always:
provideRouter(routes, { 
  paramsInheritanceStrategy: 'always'
} )

// Route Structure:
{ 
  path: 'user/:userId',
  children: [
    { 
      path: 'profile',
      component: ProfileComponent
    } 
  ]
} 

// URL: /user/101/profile
// Available in ProfileComponent with 'always':
this.route.snapshot.params['userId'] // 101

2. onSameUrlNavigation

Controls what happens when navigating to the same URL.

  • Default: 'ignore' — ignores repeated navigation to the active URL.
  • Reload: 'reload' — re-triggers navigation lifecycle events.

withInMemoryScrolling and scroll position restoration

withInMemoryScrolling() is an Angular Router feature used to manage scroll behavior during navigation. It allows Angular to restore the previous scroll position when users navigate back and scroll to the top when opening a new route.

// Enable Scrolling:
provideRouter(
  routes,
  withInMemoryScrolling({ 
    scrollPositionRestoration: 'enabled'
  } )
)

scrollPositionRestoration Options:

  1. disabled (default): No automatic scroll handling.
  2. enabled: Restores previous position on back navigation.
  3. top: Every navigation starts from scroll position 0,0.

Anchor Scrolling:

Used for URLs like /documentation#installation.

provideRouter(
  routes,
  withInMemoryScrolling({ 
    anchorScrolling: 'enabled'
  } )
)

Q. What does withInMemoryScrolling() do?

A: It configures Angular Router scroll behavior, including restoring previous scroll positions and handling anchor links.

Q. Difference between enabled and top?

A: enabled restores previous position (better for back navigation); top always scrolls to the top (better for normal page navigation).

One-Line Revision: withInMemoryScrolling() manages router scroll behavior; scrollPositionRestoration: 'enabled' restores previous scroll positions during back navigation.

Custom preloading strategy — data-driven preloading with route data

Angular's custom preloading strategy allows us to control which lazy-loaded routes should be preloaded. Instead of preloading all modules, we can use route data properties to decide dynamically which routes need background loading.

1. Add Preload Flag in Route Data

{ 
  path: 'admin',
  loadChildren: () =>
    import('./admin.routes')
      .then(m => m.ADMIN_ROUTES),
  data: { 
    preload: true
  } 
}

2. Create Custom Preloading Strategy

import {  Injectable }  from '@angular/core';
import {  PreloadingStrategy, Route }  from '@angular/router';
import {  Observable, of }  from 'rxjs';

@Injectable({ 
  providedIn: 'root'
} )
export class CustomPreloadingStrategy 
  implements PreloadingStrategy { 

  preload(
    route: Route,
    load: () => Observable<any>
  ): Observable<any> { 

    if (route.data?.['preload']) { 
      return load();
    } 

    return of(null);
  } 
}

3. Register Strategy

provideRouter(
  routes,
  withPreloading(CustomPreloadingStrategy)
)

Q. Why create a custom preloading strategy?

A: To have control over which lazy-loaded routes are preloaded instead of loading every lazy module.

Q. Where do we define the preload condition?

A: Inside the route's data property (e.g., data: { preload: true } ).

One-Line Revision: A custom preloading strategy uses route data flags to decide which lazy-loaded routes should be downloaded in the background.

Router events — NavigationStart/End/Cancel/Error, RouteConfigLoadStart/End

Angular Router emits events during the navigation lifecycle. We can subscribe to these events to track navigation status, show loaders, debug routing issues, or monitor lazy-loaded route loading.

constructor(router: Router) { 
  router.events.subscribe(event => { 
    console.log(event);
  } );
}

Navigation Events:

  • NavigationStart: Fires when navigation begins.
  • NavigationEnd: Fires when navigation completes successfully.
  • NavigationCancel: Fires when navigation is cancelled (e.g., guard returns false or redirects).
  • NavigationError: Fires when navigation fails due to an error.

Lazy Loading Events:

  • RouteConfigLoadStart: Fires when Angular starts downloading a lazy route bundle.
  • RouteConfigLoadEnd: Fires when lazy route configuration finishes loading.
// Practical Example: Global Loader
router.events.subscribe(event => { 
  if (event instanceof NavigationStart) { 
    this.loading = true;
  } 

  if (
    event instanceof NavigationEnd ||
    event instanceof NavigationCancel ||
    event instanceof NavigationError
  ) { 
    this.loading = false;
  } 
} );

Q. Difference between NavigationCancel and NavigationError?

A: NavigationCancel happens when navigation is intentionally stopped (guard/resolver issue); NavigationError happens when navigation fails due to a runtime error or loading failure.

One-Line Revision: Router events provide visibility into the navigation lifecycle: NavigationStart/End track navigation, Cancel/Error handle failures, and RouteConfigLoadStart/End track lazy loading.

Building a navigation-aware loading indicator using router events

A navigation loading indicator in Angular is built by listening to Router events. We show the loader when navigation starts and hide it when navigation completes, is cancelled, or fails.

@Injectable({ 
  providedIn: 'root'
} )
export class LoadingService { 
  loading = signal(false);

  show() {  this.loading.set(true); } 
  hide() {  this.loading.set(false); } 
} 

// Router Event Listener:
constructor(router: Router, loadingService: LoadingService) { 
  router.events.subscribe(event => { 
    if (event instanceof NavigationStart || event instanceof RouteConfigLoadStart) { 
      loadingService.show();
    } 

    if (
      event instanceof NavigationEnd ||
      event instanceof NavigationCancel ||
      event instanceof NavigationError ||
      event instanceof RouteConfigLoadEnd
    ) { 
      loadingService.hide();
    } 
  } );
}

Q. Why not show loader only on NavigationStart and hide on NavigationEnd?

A: Because navigation can also fail or be cancelled. Handling NavigationCancel and NavigationError prevents the loader from getting stuck.

One-Line Revision: A navigation-aware loader listens to router lifecycle events: show on NavigationStart/RouteConfigLoadStart and hide on NavigationEnd, NavigationCancel, NavigationError, or RouteConfigLoadEnd.

RouterOutlet lifecycle: (activate) and (deactivate) events

RouterOutlet provides lifecycle events that notify when a routed component is created or removed. The activate event fires when Angular loads a component into the outlet, and deactivate fires when Angular removes that component during navigation.

// Usage in Component
onActivate(component: any) { 
  console.log('Loaded:', component);
} 

onDeactivate(component: any) { 
  console.log('Removed:', component);
}

Practical Use Cases:

  • Track Page Components for analytics.
  • Cleanup Logic upon leaving pages.
  • Dynamic Component Interaction (calling methods on activated instances).

Q. When does activate run?

A: When Angular creates and attaches the routed component to the outlet.

Q. When does deactivate run?

A: When Angular destroys the current routed component because navigation moved away.

One-Line Revision: RouterOutlet's activate event runs when a routed component is loaded, and deactivate runs when it is removed during navigation.

ROUTER_OUTLET_DATA — passing reactive signal data from parent outlet to child component

ROUTER_OUTLET_DATA allows a parent component to pass reactive data to a routed child component through RouterOutlet. The data is provided as a signal, so the child can react to changes without using services or inputs.

<!-- Parent Template -->
<router-outlet [routerOutletData]="userData"></router-outlet>
// Parent Component
userData = signal({  role: 'admin', theme: 'dark' } );

// Child Component
export class ChildComponent { 
  outletData = inject(ROUTER_OUTLET_DATA);
}

Q. What type of data does ROUTER_OUTLET_DATA provide?

A: It provides a reactive signal containing data passed from the parent RouterOutlet.

One-Line Revision: ROUTER_OUTLET_DATA passes reactive signal data from a parent RouterOutlet to routed child components without requiring services or route parameters.

UrlMatcher — matching routes by numeric ID or slug

UrlMatcher allows custom route matching logic when Angular's default path matching is not enough. Instead of using a static path, we provide a function that decides whether a URL segment matches a route.

// Custom Matcher Example (Numeric ID Only)
export const numericIdMatcher: UrlMatcher = (segments: UrlSegment[]) => { 
  if (segments.length === 1 && /^\d+$/.test(segments[0].path)) { 
    return {  consumed: segments } ;
  } 
  return null;
} ;

// Route declaration
{  matcher: numericIdMatcher, component: UserComponent }

Q. What happens if UrlMatcher returns null?

A: Angular considers the route not matched and checks other available routes.

One-Line Revision: UrlMatcher provides custom route matching logic when standard Angular path matching cannot handle specific URL patterns like numeric IDs or slugs.

Signals integration — isActive signal, withViewTransitions

Angular Router integrates with Signals to provide reactive routing state. RouterLinkActive exposes an isActive signal to track whether a route is currently active. withViewTransitions() integrates the browser View Transitions API to create smooth animations between route changes.

// 1. View Transitions Setup
provideRouter(
  routes,
  withViewTransitions()
)
/* 2. Example CSS Animation */
::view-transition-old(root) {  animation: fade-out 200ms; } 
::view-transition-new(root) {  animation: fade-in 200ms; }

Q. Does Angular create the animations itself?

A: No. Angular integrates with the browser View Transitions API. Developers define the animation styles using CSS.

One-Line Revision: isActive provides reactive active-route tracking through Signals, while withViewTransitions() enables smooth browser-based animations during navigation.

withNavigationErrorHandler — redirecting to a 404 page on resolver errors

withNavigationErrorHandler() provides a global way to handle navigation errors. If a resolver, lazy loading, or route activation throws an error, we can catch it centrally and redirect the user to an error page like 404 instead of handling errors in every route.

provideRouter(
  routes,
  withNavigationErrorHandler(() => { 
    const router = inject(Router);
    return router.createUrlTree(['/404']);
  } )
)

Q. What errors can withNavigationErrorHandler handle?

A: Navigation errors caused by resolvers, guards, lazy-loaded routes, or route activation failures.

One-Line Revision: withNavigationErrorHandler() catches router navigation failures globally and can redirect users to fallback pages like 404 when resolvers or routes fail.

Named outlets — how they work and why to avoid them

Named outlets allow multiple routed components to be displayed at the same time using multiple <router-outlet> instances with different names.

<!-- Outlets -->
<router-outlet></router-outlet>
<router-outlet name="chat"></router-outlet>

// Navigation
this.router.navigate([{  outlets: {  chat: ['chat'] }  } ]);
// URL: /home(chat:chat)

Why Avoid Named Outlets?

  • Complex URLs: E.g., /products(chat:open;help:faq).
  • Difficult Navigation: Complex navigation object structures required.
  • State Management Complexity: Multiple active route trees are harder to coordinate.

Q. Why are named outlets less common today?

A: They add routing complexity, and many use cases can be handled more simply with component composition, dialogs, or signals.

One-Line Revision: Named outlets allow multiple routed components simultaneously, but they should be used carefully because they make URLs and navigation logic more complex.
